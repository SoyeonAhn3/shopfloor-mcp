# 생산 데이터 MCP 서버: 데이터셋 설계서

> 최종 수정: 2026-10-21
> 기획서(01_production-mcp-server.md)의 3-4 데이터셋 항목을 구체화한 문서

## 1. 목적

- MCP 서버가 조회하고 분석할 **현실적인 가상 생산 데이터**를 만든다.
- 평가 시나리오의 정답이 명확하도록 **정답 사건을 의도적으로 심는다.**
- 데이터를 만들 때 **사건별 정답 수치를 함께 계산해 정답표로 남겨서**, 평가 검수를 정답표 대조로 할 수 있게 한다.

---

## 2. 기본 설정

| 항목 | 내용 |
|---|---|
| 기간 | 2026-07-01 ~ 2026-09-30 (3개월, 66 생산일) |
| 기준 시각 | 2026-10-01(목) 08:00 고정 (서버의 "현재") |
| 라인 | 6개 |
| 가동일 | 월~금. 주말은 휴무, 공휴일은 두지 않는다 |
| 교대 | 2교대. A조와 B조가 매주 월요일에 주간과 야간을 바꾼다 |
| 주간 | 08:20 ~ 20:00 (11시간 40분) |
| 야간 | 20:20 ~ 다음날 08:00 (11시간 40분). 금요일 야간은 토요일 08:00까지 |
| 교대 시간 | 08:00 ~ 08:20, 20:00 ~ 20:20 (계획 정지, 생산 없음) |
| 하루 가동 시간 | 23시간 20분 |
| 생산일 기준 | 주간 시작(08:20)부터 다음날 야간 종료(08:00)까지를 하루로 본다 |

- 생산일 수: 7월 23일, 8월 21일, 9월 22일

**생산일 기준의 의미**
- 7월 15일 생산일 = 7월 15일 08:20 ~ 7월 16일 08:00
- 7월 16일 새벽 3시에 일어난 일은 **7월 15일 생산일의 야간**에 속한다.
- 금요일 생산일은 토요일 08:00에 끝난다. 토요일 새벽 3시에 일어난 일은 **금요일 생산일의 야간**에 속한다.
- 서버의 상대 기간 해석("어제", "이번 주")과 정답표는 모두 이 기준을 따른다.

**기준 시각의 의미**
- 2026-10-01(목) 08:00은 9/30(수) 생산일이 끝나고, 10/1 생산일(08:20 시작)은 아직 시작 전인 시점이다.
- 9/30 생산일의 야간은 10/1 08:00에 끝나므로, 원데이터의 마지막 시각은 2026-10-01 08:00이다.
- "어제"는 9/30 생산일, "이번 주"는 9/28(월) ~ 9/30, "지난주"는 9/21 ~ 9/25, "지난달"은 9월이다. 주의 시작은 월요일로 본다.
- "오늘", "이번 달"은 조회 가능 범위 밖이다. 서버는 "10월 생산일은 아직 시작 전입니다. 조회 가능 범위는 7/1~9/30입니다. 9월 기준으로 볼까요?"처럼 안내한다.
- 주말 날짜는 `휴무일`로 답한다. 토요일 00:00 ~ 08:00은 금요일 생산일의 야간이라는 점을 함께 안내한다.

## 3. 데이터 아키텍처

### 3-1. 전체 흐름

```
생성 설정 (라인 정보, 평상시 규칙, 사건 E1~E9, 고정 시드)
  │
  ├──► 데이터 생성기 ──► 기본 DB  production.db
  │                        │  검증기가 8장의 검증 규칙 확인
  │                        │
  │                        ├─ 개발·데모: 복사본 하나로 서버 실행
  │                        └─ 평가: 시나리오마다 새 복사본
  │                                │
  │                                ▼
  │                           MCP 서버
  │                            ├─ 조회 도구: 읽기 전용으로 연결
  │                            └─ 초안·확정·감사 기록: 해당 테이블만 쓰기
  │                                │
  │                                ▼
  │                           평가 실행기 ──► 평가 기록 (JSON) ──► 결과 재생 페이지
  │                                ▲
  └──► 정답표  answer_key.json ────┘ (채점할 때 대조)
```

### 3-2. 설계 원칙

**① 계획과 실적을 다른 테이블에 둔다**

기획서의 상태 6가지가 데이터 구조만으로 구분된다. "생산 없음"과 "미입력"의 구분이 서버의 추측이 아니라 데이터 구조로 보장된다.

| 상태 | 데이터에서 보이는 모습 |
|---|---|
| 기간 밖 | 캘린더에 날짜가 없음 (예: 10월) |
| 휴무일 | 캘린더에서 근무일이 아님 (주말) |
| 계획 정지 | 계획 행은 있는데 목표가 0 (E5). 교대 시간처럼 일부만 계획 정지면 그만큼 목표가 줄어듦 |
| 데이터 미입력 | 목표가 0보다 크고 실적 행이 없음 (E6) |
| 생산 0 | 목표가 0보다 크고 실적 행은 있는데 생산이 0 |
| 조회 실패 | DB 오류 |

**② 원데이터에는 사건 표시를 두지 않는다**

DB에는 "이 기록이 E4"라는 칼럼이 없다. 사건 정보는 정답표에만 있다. 서버나 Claude가 표시를 보고 정답을 맞히는 일을 막기 위해서다.

**③ 정답표는 생성 설정에서 바로 만든다**

"E1은 2라인 10:00~14:00 정지"처럼 심은 값에서 정답을 계산하고, 서버는 원데이터만 보고 따로 계산한다. 두 경로가 분리되어야 서버 계산에 버그가 있을 때 평가에서 걸린다.

**④ 조회 도구는 읽기 전용으로 연결한다**

코드에 버그가 있어도 조회 도구로는 생산 데이터를 바꿀 수 없다. 쓰기는 초안, 확정, 감사 기록에만 허용한다.

**⑤ 기본 DB는 바꾸지 않고, 실행할 때마다 복사본을 쓴다**

- 평가는 시나리오마다 새 복사본에서 시작한다. 앞 시나리오에서 등록된 이슈 때문에 다음 시나리오가 중복 방지에 걸리지 않는다.
- 시나리오가 끝나면 실행기가 이슈와 감사 기록의 변화를 뽑아 평가 기록에 넣는다. "이슈 기록이 그대로인가"는 이 비교로 채점한다.

**⑥ 데이터 버전을 남긴다**

새로 생성할 때마다 `dataset_version`을 발급하고 실제 생성 시각(`generated_at`)과 시드를 `dataset_meta`에 기록한다. 생성 시각이 다르면 생산 수치가 같아도 다른 생성본이다. 평가 기록과 결과 재생 페이지에는 이 생성본의 식별값을 표시한다. 평가를 위해 DB를 복사할 때는 원본의 식별값과 생성 시각을 유지한다.

생산 내용이 같은 조건에서 재현되는지 확인하는 반복 생성 검사는 생성본 구분과 별개다. 검사 채택 여부와 비교 범위는 추가 논의하며, 서로 다른 생성본의 식별값과 생성 시각이 같아야 한다는 조건은 두지 않는다.

**⑦ 작업자 ID는 데이터에만 둔다**

어떤 도구 응답에도 작업자 ID를 넣지 않는다. 응답에 ID가 있으면 Claude가 직접 세어 개인별 순위를 만들 수 있기 때문이다. 집계는 라인과 교대조 단위까지만 한다.

### 3-3. 수집 방식 가정

| 데이터 | 어떻게 쌓이는가 |
|---|---|
| 생산 수량, 양품 수량 | 설비 카운터가 자동으로 집계하고 시간대별로 저장 |
| 비가동 시작·종료 | 설비 신호로 자동 기록 (그래서 몇 분짜리 순간 정지도 남음) |
| 비가동 사유·메모 | 작업자가 나중에 입력 (그래서 메모는 사람이 쓴 자유 입력 칸) |
| 불량 | 검사 작업자가 발견할 때마다 1건씩 등록 |
| 미입력(E6) | 설비 통신 장애로 해당 시간대 실적이 집계되지 않음 |

### 3-4. 공통 규칙

- 칼럼 이름은 영어로 쓴다. 분류 값은 영어 코드로 저장하고, 서버가 응답할 때 한국어로 바꾼다. (예: `day` → 주간)
- 생산 기록과 기준 시각은 공장 현지 시각을 `YYYY-MM-DDTHH:MM` 형식의 텍스트로 저장한다. 실제 생성 시각인 `dataset_meta.generated_at`은 예외로, 밀리초와 `Z`를 포함한 UTC ISO 형식을 쓴다.
- 시간대는 정각 시작 시각(`slot_start`)으로 구분한다. (예: 09시대 = `…T09:00`)
- 생산일은 생성할 때 미리 계산해서 칼럼으로 넣는다.
- 목표 수량 = 계획 가동 분 × 시간당 표준 생산량 ÷ 60. 이 정의가 있어야 "세 손실의 합 = 목표 − 양품 수량"이 정확히 맞는다.

### 3-5. 테이블

**A. 생성 데이터 (생성기가 만들고, 서버는 읽기만 함)**

#### `dataset_meta`: 데이터 버전과 기준 시각 (1행)

| 칼럼 | 타입 | 설명 | 예시 |
|---|---|---|---|
| dataset_version | TEXT | 새 생성본마다 발급하는 고유 식별값. DB 복사본과 해당 정답표는 원본 값을 유지 | `ds-7f3a9c…` |
| seed | INTEGER | 고정 시드 | `20260701` |
| period_start | TEXT | 첫 생산일 | `2026-07-01` |
| period_end | TEXT | 마지막 생산일 | `2026-09-30` |
| reference_now | TEXT | 서버의 "현재" | `2026-10-01T08:00` |
| generated_at | TEXT | 데이터를 실제로 생성한 시각 (UTC ISO) | `2026-10-22T01:15:00.000Z` |

#### `lines`: 라인 정보 (6행)

| 칼럼 | 타입 | 설명 | 예시 |
|---|---|---|---|
| line_id | TEXT, 기본 키 | 라인 ID | `L4` |
| line_name | TEXT | 표시 이름 | `4라인` |
| product_name | TEXT | 생산 제품 | `기판 조립` |
| std_rate_per_hour | INTEGER | 시간당 표준 생산량 | `180` |

#### `workers`: 작업자 (24행)

| 칼럼 | 타입 | 설명 | 예시 |
|---|---|---|---|
| worker_id | TEXT, 기본 키 | 작업자 ID (가상 ID만 사용) | `W-L4-A2` |
| line_id | TEXT | 소속 라인 | `L4` |
| crew | TEXT | 소속 교대조 `A` / `B` | `A` |

#### `calendar`: 근무 캘린더 (92행)

| 칼럼 | 타입 | 설명 | 예시 |
|---|---|---|---|
| calendar_date | TEXT, 기본 키 | 날짜 | `2026-09-14` |
| day_of_week | TEXT | 요일 `mon` ~ `sun` | `mon` |
| is_working_day | INTEGER | 1 근무일 / 0 휴무일 | `1` |
| week_start | TEXT | 그 주의 월요일 | `2026-09-14` |
| day_crew | TEXT | 주간 담당 조 (휴무일은 비움) | `B` |
| night_crew | TEXT | 야간 담당 조 (휴무일은 비움) | `A` |

#### `hourly_plan`: 시간대별 계획 (9,504행)

| 칼럼 | 타입 | 설명 | 예시 |
|---|---|---|---|
| line_id | TEXT | 라인 | `L4` |
| slot_start | TEXT | 시간대 시작 시각 | `2026-09-15T09:00` |
| production_date | TEXT | 생산일 | `2026-09-15` |
| shift | TEXT | `day` 주간 / `night` 야간 | `day` |
| crew | TEXT | 담당 교대조 | `B` |
| hour_of_day | INTEGER | 시각. 시간대별 패턴 분석에 사용 | `9` |
| planned_stop_minutes | INTEGER | 계획 정지 분 (교대, 설비 점검) | `0` |
| planned_stop_reason | TEXT | `shift_change` 교대 / `maintenance` 설비 점검 / 없음 | NULL |
| planned_minutes | INTEGER | 계획 가동 분 = 60 − 계획 정지 분 | `60` |
| target_qty | INTEGER | 목표 = 계획 가동 분 × 표준 생산량 ÷ 60 | `180` |

- 기본 키: (line_id, slot_start). 근무일에만 행이 있다.
- 08시대, 20시대: 계획 정지 20분(`shift_change`), 계획 가동 40분, 목표는 표준 생산량의 2/3
- E5 하루의 24개 행: 계획 정지 60분(`maintenance`), 계획 가동 0분, 목표 0

#### `hourly_output`: 시간대별 실적 (9,500행)

| 칼럼 | 타입 | 설명 | 예시 |
|---|---|---|---|
| line_id | TEXT | 라인 | `L4` |
| slot_start | TEXT | 시간대 시작 시각 | `2026-09-15T09:00` |
| produced_qty | INTEGER | 생산 수량 | `151` |
| good_qty | INTEGER | 양품 수량 (생산 수량 이하) | `139` |

- 기본 키: (line_id, slot_start). 같은 키로 `hourly_plan`과 연결된다.
- **E6 미입력 시간대는 행 자체가 없다.** 계획 행은 있는데 실적 행이 없으면 "미입력"이다.

#### `defect_events`: 불량 기록 (기본 설정 50,244행, 1행 = 불량 1개)

| 칼럼 | 타입 | 설명 | 예시 |
|---|---|---|---|
| defect_id | TEXT, 기본 키 | 불량 기록 ID | `DF-041237` |
| line_id | TEXT | 작업장 (라인) | `L4` |
| production_date | TEXT | 생산일 | `2026-09-15` |
| detected_at | TEXT | 발견 시각 (분 단위) | `2026-09-15T09:23` |
| shift | TEXT | `day` / `night` | `day` |
| crew | TEXT | 교대조 | `B` |
| defect_type | TEXT | 불량 유형 (4-2 참고) | `dimension` |
| worker_id | TEXT | 불량을 등록한 작업자 | `W-L4-B2` |

- 불량이 없으면 행도 없다. 미입력은 `hourly_output`에 행이 있는지로 판정한다.
- 시간대마다 불량 기록 수 = 그 시간대의 생산 수량 − 양품 수량
- 작업자는 불량을 등록한 사람(검사자)이다. 불량을 만든 사람이 아니다.

#### `downtime_events`: 비가동 (기본 설정 439행)

| 칼럼 | 타입 | 설명 | 예시 |
|---|---|---|---|
| downtime_id | TEXT, 기본 키 | 비가동 ID | `DT-00412` |
| line_id | TEXT | 라인 | `L5` |
| production_date | TEXT | 시작 시각 기준 생산일 | `2026-08-14` |
| shift | TEXT | `day` / `night` | `night` |
| crew | TEXT | 교대조 | `B` |
| start_at | TEXT | 시작 시각 | `2026-08-14T23:30` |
| end_at | TEXT | 종료 시각 | `2026-08-15T02:30` |
| duration_min | INTEGER | 정지 시간 (분) | `180` |
| reason_category | TEXT | 대분류 (4-3 참고) | `equipment` |
| reason_code | TEXT | 세부 사유 (4-3 참고) | `breakdown` |
| is_planned | INTEGER | 1 계획 / 0 비계획 | `0` |
| memo | TEXT | 자유 메모. 서버는 응답할 때 "참고 데이터"로 감싸서 전달 | `벨트 교체 후 재가동` |
| entered_by | TEXT | 사유와 메모를 입력한 작업자 | `W-L5-B1` |

- 예시 행은 E7이다. 날짜는 토요일(8/15)로 넘어가지만 생산일은 금요일(8/14)이다.
- E5는 교대 시간과 겹치지 않도록 주간과 야간 2건으로 나눠 기록한다.

**B. 실행 중에 쌓이는 데이터 (서버가 씀)**

#### `issues`: 이슈 (초기 25행 + 등록분)

| 칼럼 | 타입 | 설명 | 예시 |
|---|---|---|---|

## 5. 평상시 데이터를 만드는 규칙

정답 사건이 아닌 **평소의 자연스러운 흔들림**을 만드는 규칙이다. 사건이 이 흔들림 속에 묻히지 않으면서도, 데이터가 너무 깨끗해 보이지 않게 한다.

| 항목 | 규칙 |
|---|---|
| 생산량 | 시간당 표준 생산량의 일정 범위 안에서 무작위로 흔들림 |
| 순간 정지 | 라인별로 하루 평균 1건, 짧은 시간의 정지가 무작위로 발생 |
| 불량률 | 라인별 기본 불량률 범위 안에서 흔들림 (전체 평균 약 2% 가정) |
| 불량 기록 | 불량 1개마다 1건. 발견 시각은 해당 시간대 안에서 정하고, 교대 시간은 피한다 |
| 정지와 생산의 일치 | 비가동 시간만큼 해당 시간대 생산량이 줄어든다 |
| 교대 시간 | 08:00 ~ 08:20, 20:00 ~ 20:20에는 생산이 없다 |
| 주말 | 토요일 08:00 ~ 월요일 08:20에는 어떤 기록도 없다 |
| 비가동 배치 | 교대 시간과 겹치지 않고, 생산일 경계(08:00)를 넘지 않는다. 자정은 넘을 수 있다 |
| 재현성 | 같은 생성기·설정에서 생산 내용이 재현되도록 고정 시드를 사용한다. 새 생성본은 별도로 식별하며, 반복 생성 검사 채택 여부는 추가 논의한다 |

- 평가 검수는 AI의 답변을 이 정답표와 대조하는 방식으로 한다.
- 정답표의 달성률은 모두 양품 수량 기준이다.
- 정답표는 생성 설정의 심은 값에서 직접 계산하고, 서버의 계산 코드를 쓰지 않는다. (3-2 ③)
- 정답표는 데이터와 같은 규칙으로 계산되므로, 데이터를 다시 만들면 정답표도 같이 다시 만들어진다.

## 8. 데이터 검증 규칙

데이터를 만든 뒤 아래를 자동으로 확인한다.

| 규칙 | 확인 내용 |
|---|---|
| 교대 시간 | 08시대·20시대에 계획 가동이 40분 이내이고 생산량도 그 상한을 넘지 않는지 |
| 목표 조정 | 08시대, 20시대 목표가 40분 기준으로 계산됐는지 |
| 목표 정의 | 모든 시간대 목표가 계획 가동 분 × 표준 생산량 ÷ 60인지 |
| 정지와 생산 | 비계획 정지 분을 뺀 가동 가능 수량을 넘지 않고, 전 시간 정지 시 생산 0인지 |
| 양품 | 양품 수량이 생산 수량보다 크지 않은지 |
| 불량 수 | 시간대마다 불량 기록 수 = 생산 수량 − 양품 수량인지 |
| 불량 위치 | 실적이 없는 시간대(E6)와 교대 시간에는 불량 기록이 없는지 |
| 손실 분해 | 별도 불량 행수로 계산한 비가동 손실 + 속도 저하 손실 + 불량 손실 = 목표 − 양품 수량이고, 각 손실이 음수가 아닌지 |
| 계획 정지 | E5 비가동 기록이 계획으로 표시되고, 그날 목표가 0인지 |
| 사유 코드 | 대분류가 `planned`이면 `is_planned` = 1이고, 아니면 0인지 |
| 비가동 배치 | 교대 시간과 겹치지 않고, 생산일 경계(08:00)를 넘지 않는지 |
| 휴무일 | 생산일이 휴무일인 계획, 실적, 비가동, 불량 기록이 없는지 |
| 교대조 | 모든 기록의 교대조가 캘린더의 담당 조와 일치하는지 |
| 생산일 | 자정 이후 야간 기록이 전날 생산일로 묶이는지 (금요일 야간의 토요일 새벽 포함) |
| 사건 존재 | 정답 사건 9개가 모두 데이터에 들어 있는지 |
| 정상 라인 | 6라인에 사건이 없는지 |
| 이슈 이력 | 과거 이슈에 E4 관련 이슈가 없는지 |

Phase 1의 검증기는 이 순서대로 V01~V17을 구현했다. 시간대별 생산 합계만 있으므로 제품별 생산 분까지 직접 증명할 수는 없다. 교대 20분 제외는 계획과 생산 상한으로 확인하고, 불량·비가동의 실제 시각은 별도 규칙으로 검사한다. 외래키·SQLite 무결성 및 DB와 정답표의 생성본 일치도 확인한다.

## 9. 실제 생산 데이터 구조와의 비교

현장의 시간대별 생산 현황판이나 MES 집계 리포트 수준과 비슷하게 맞추고, 그 뒤의 원천 시스템(생산 오더, 설비 신호, 코드 체계)보다는 단순하게 둔다.

| 우리 테이블 | 실제로 대응하는 것 | 단순화한 점 |
|---|---|---|
| `lines` | 작업장(라인) 마스터 | 한 라인이 한 제품만 생산, 품번별 표준 속도 없음 |
| `calendar` | 공장 근무 캘린더 | 공휴일 없음 |
| `hourly_plan` | 시간대별 생산 현황판의 계획 칸 | 생산 오더 없이 시간대 목표만 둠 |
| `hourly_output` | 현황판의 실적 칸, MES 실적 집계 | 원천인 설비 카운터 신호는 두지 않음 |
| `defect_events` | MES 불량 등록 | 불량 유형 3개, 공정·위치·재작업 구분 없음 |
| `downtime_events` | MES 비가동 이벤트 | 설비 단위 없이 라인 단위로 기록 |
| `issues` | 품질·설비 이슈 관리 | 담당자, 조치 기한, 원인과 대책 칸 없음 |

**계산 개념은 업계 표준을 따른다**
- 원인 분해는 OEE 손실 구조와 같다. 비가동, 속도 저하, 불량이 각각 시간 가동률, 성능 가동률, 양품률에 대응한다.
- 계획 정지를 손실에서 빼는 것은 OEE의 "계획 가동 시간" 개념과 같다.
- 달성률(양품 ÷ 목표)은 표준 생산량을 설비의 이론 최대 속도로 볼 때 OEE와 같은 값이다.
- 생산일을 첫 교대 시작부터 세는 방식은 실제 공장에서 흔하다.

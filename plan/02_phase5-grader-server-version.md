# Phase 5 후속: 값 채점 개선(7번)과 서버 버전 식별

> 최종 수정: 2026-10-28
> Phase 5 후속 개선 7번과 실행 계획 2단계(서버 버전 구분)를 구체화한 작업 계획
> 상태: 2026-10-28 구현 완료. 결과는 `Phase/Phase5_Evaluation.md`의 "Follow-up #7 and server build identification" 절에 있다.

## 1. 목적

- 값 검사가 **관계없는 숫자로 통과하는 문제**를 막는다. 평가 S11에서는 날짜 "9/14"의 14가 A조 정지 횟수 14회로 인정되었다.
- 실행 기록에 **실제로 실행된 서버 빌드**를 남기고, fine/coarse 비교는 같은 서버 빌드끼리만 짝짓는다.
- 유료 실행 없이 끝낸다. 모델 입력(도구 설명, 정책, 시스템 프롬프트)은 바꾸지 않는다.

## 3. A. 값 채점 개선 (`src/eval/grade.ts`)

### 3-1. 판정 기준

| 경우 | 판정 |
|---|---|
| 정답과 일치하는 숫자가 있고, 그중 하나라도 가장 가까운 항목명이 그 필드의 것 | `pass` |
| 정답과 일치하는 숫자가 있지만 가장 가까운 항목명이 다른 필드의 것이거나 항목명이 없음 | `needs_review` |
| 정답과 같은 숫자가 날짜·시각·식별자 안에만 있음 | `needs_review` (리뷰 반영: 처음 계획은 `fail`) |
| 정답과 일치하는 숫자가 없음 | `fail` |
| 항목명 규칙이 없는 필드 | 숫자가 일치해도 `needs_review` (항목명 없이 통과시키지 않는다) |

`matchesValue()`의 반환 형태(`true` / `false` / `null`)는 유지한다. `null`이 `needs_review`가 된다.

### 3-2. 후보에서 빼는 숫자

아래 범위의 숫자는 값 후보에서 뺀다. 위치가 바뀌지 않도록 같은 길이의 공백으로 가린 뒤 후보를 찾는다.
항목명 확인은 가리기 전 원문에서 한다. 가린 범위 안에서 정답과 같은 숫자는 통과시키지 않고 검수로 넘긴다.
"정지 3/5회"처럼 실제 답이 가려질 수 있어 자동 실패로 두지 않는다.

- 날짜: `9/14`, `9월 14일`, `2026-09-14`, `9/14~18`. 기존 `datesIn()` 정규식은 `.`도 날짜 구분자로 보므로
  가리는 데 쓰면 `1.72%` 같은 소수가 지워진다. 그래서 `.`은 연도 뒤에서만 날짜로 보는 별도 패턴을 쓴다.
- 시각: `09:14`, `21시`
- 식별자: `Q-0014` 같은 근거 ID, `L3`, `3번 라인`

### 3-3. 항목명 규칙

정답표 필드 이름의 끝부분으로 규칙을 고른다. 근거는 정답표 필드 정의와 `resources/glossary.md`의 용어다.

| 필드 (끝부분) | 근처에 있어야 할 말 |
|---|---|
| `produced` | 생산 |
| `good` | 양품 |
| `target`, `adjustedTargets.*` | 목표 |
| `achievement`, `weekAverage` | 달성 |
| `defectRate`, `baselineDefectRate` | 불량률, 불량 |
| `defects` | 불량 |
| `delta`, `change_pct` | 증감, 증가, 감소, 차이, 변화, 대비, 늘, 줄 |
| `downtimeCount` | 정지, 비가동, 횟수, 또는 숫자 바로 뒤 `회`·`건`·`번` |
| `downtimeMinutes`, `totalDowntimeMin`, `durationMin` | 정지, 비가동, 지속, 또는 숫자 바로 뒤 `분` |
| `plannedMinutes` | 계획 |
| `outputPerPlannedMinute` | 분당 |
| `ratioToNormal` | 평소, 정상, 또는 숫자 바로 뒤 `배` |

- 현재 개발용·평가용 시나리오의 숫자 값 검사 109개가 모두 위 규칙에 해당한다. 필드 이름은 대소문자를 구분하지 않고,
  끝에 붙은 날짜·번호 키(`dailyAchievement.2026-09-14`)를 떼고 찾는다.
- "근처"는 같은 줄에서 숫자 앞 20자·뒤 12자 안의 같은 구다. 문장 끝·괄호·세미콜론에서 끊고, 그 안에서 **가장 가까운**
  항목명이 그 필드의 것이어야 한다(리뷰 반영: "생산 4,210개, 양품 4,100개"에서 4,210이 양품으로 통과하던 문제).
  쉼표 뒤에 나열한 값은 다른 항목명이 나오기 전까지 앞의 항목명을 이어받고, 숫자 뒤 괄호 속 부연은 건너뛴다.
  "분당 생산량"처럼 긴 항목명 안의 짧은 항목명("생산")은 따로 세지 않는다.
- 숫자 바로 뒤 단위가 다른 수량의 것이면(정지 횟수에 `분`, 1분당 생산량에 `건`) 통과하지 않는다. 주변에 항목명이 없을 때만
  `회`·`건`·`번`, `분`, `배` 단위로 횟수·시간·배수를 인정한다.
- 마크다운 표 칸은 먼저 그 칸을 보고, 없으면 그 열의 제목이나 그 행의 첫 칸에 그 필드의 항목명이 있는지 본다.
- 글자 수와 위 규칙은 합성 문장 테스트와 D 세트 기록으로만 정했다.
- 기존 규칙은 유지한다: 비율은 백분율로 비교, 백분율 정답은 `%` 필수, 음수 증감은 "150개 감소" 허용.

### 3-4. 한계 (사람 검수로 남김)

- 라인·조·날짜가 섞인 경우(L2 숫자가 L1 항목명 옆에 있는 경우)는 구분하지 못한다.
- S12 fine의 "3개"(정답 2.92) 같은 반올림 일치는 근처에 "분당"이 있으면 여전히 통과할 수 있다. 허용 오차는 바꾸지 않기로 했다.

## 4. B. 서버 빌드 식별

| 항목 | 내용 |
|---|---|
| 새 필드 | `RunRecord.serverBuildHash` (선택 필드) |
| 계산 대상 | 평가가 실제로 실행하는 빌드 파일: `dist/core`, `dist/server`, `dist/shared`, `dist/resources`. 실행되지 않는 `.d.ts`·`.map`은 제외(리뷰 반영) |
| 계산 방식 | 상대 경로 순으로 정렬한 각 파일의 `textHash()`를 묶어 다시 `textHash()` |
| 계산 위치 | 함수는 `src/eval/config.ts`(`descriptionsHash()` 옆), 호출은 `src/eval/runner.ts` `runBatch()` 시작 시 한 번. 실행 중 바뀌면 기존 설명·정책 해시 검사처럼 실패 처리 |
| 비교 조건 | `src/eval/summary.ts`의 fine/coarse 짝 조건(`limits`, `pricing`, `graderHash`)에 추가 |

- **소스가 아닌 빌드를 해시하는 이유:** 평가는 `dist/server/index.js`를 실행하고 서버는 `dist/resources`를 읽는다.
  빌드가 오래된 상태로 실행해도 기록이 실제 실행본을 가리킨다.
- **`graderHash`처럼 `nullable().default(null)`로 두지 않는 이유:** 기본값이 생기면 기존 기록을 다시 직렬화할 때
  `serverBuildHash: null`이 추가되어 `recordHash`가 바뀌고, 기존 검수 파일과의 연결이 끊긴다.
  선택 필드로 두면 기존 기록의 직렬화 결과가 그대로다.
- 기존 v1 기록에는 값이 없으므로 v1끼리만 짝이 된다. 새 기록은 같은 빌드끼리만 짝이 된다.
- 지운 소스의 옛 빌드 파일이 `dist/`에 남아 있으면 해시가 달라질 수 있다. 이 경우 짝이 안 되는 쪽으로만 틀리므로
  잘못 비교하지는 않는다. 기준점 실행 전에는 깨끗한 빌드를 쓴다.

## 5. 평가 무결성

- 규칙과 글자 수는 합성 문장 테스트와 개발용 D 세트 기록으로만 정한다. S 기록 답변은 규칙을 정하는 데 보지 않는다.
- v1 S 기록 재채점 비교표는 규칙을 확정한 뒤 마지막에 한 번만 출력한다. 비교표를 보고 규칙을 다시 고치지 않는다.
  출력은 세션 임시 폴더의 일회성 스크립트로 하고 저장소에는 아무것도 저장하지 않는다.
  실제로는 두 번 출력했다. 코드 리뷰 전 규칙으로 한 번, 리뷰를 반영한 최종 규칙으로 한 번이다. 리뷰 반영과 그 뒤의 D 세트 조정은
  리뷰가 든 합성 사례와 D 기록에서 나왔고, 첫 출력을 보고 고친 것이 아니다. 문서에는 최종 출력만 수치로 남긴다.
- `grade.ts`가 바뀌면 `graderHash`가 자동으로 바뀐다. 새 기록과 v1 기록은 비교 조건이 달라 짝이 되지 않는다(의도한 동작).
- `src/server/descriptions.ts`, 정책, 시나리오, 잠금, 동결 기록은 바꾸지 않는다. 재동결이 필요 없다.
- 영구 재채점(같은 채점기로 v1·v2를 맞추는 작업)은 후속 10번 비교 실행 때 별도로 정한다. (2026-10-29: 10번을 하지 않기로 해서 영구 재채점도 하지 않는다)

## 6. 구현 단계

1. 채점 실패 테스트 작성 (`tests/eval/grade.test.ts`): 날짜·시각·ID 속 숫자 제외, 항목명 있음 → 통과,
   항목명 없음 → `needs_review`, 표 머리글 항목명, 규칙 없는 필드 → `needs_review`. 기존 테스트 문장에 항목명이 없으면
   문장에 항목명을 넣고 기대값은 그대로 둔다.
2. `grade.ts`에 가리기와 항목명 규칙 구현.
3. D 세트 회귀 확인: 개발용 실행 9회의 기록을 새 채점기로 다시 채점해 값 검사 판정 변화를 출력하고 확인한다(일회성 스크립트, 저장 없음).
4. 서버 빌드 실패 테스트 작성: 필드가 없는 기록의 `recordHash` 불변, 빌드가 다른 fine/coarse는 짝이 안 됨,
   실행 기록에 빌드 해시 기록.
5. `record.ts`, `runner.ts`, `summary.ts` 구현.
6. 기존 검수 파일 전부의 `recordHash`가 기록과 여전히 일치하는지 확인(일회성 스크립트).
7. v1 S 기록 재채점 비교표 출력 (5절 조건).
8. 문서: Phase 5 영문·국문(7번 상태, 서버 빌드 식별, 변경 이력), README·README_ko 테스트 수와 문서 목록, `docs/MCP_SETUP.md` 테스트 수.
9. `npm run check` 통과, 리뷰 AI 한 번, 커밋은 사용자 요청 시.
